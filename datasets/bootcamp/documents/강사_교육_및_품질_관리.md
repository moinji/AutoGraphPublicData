## 2. 교수법 가이드라인

### 2.1 강의 운영 원칙

본 부트캠프의 교수법은 다음 5가지 원칙에 기반합니다:

1. 실습 중심 (Practice-First): 이론 30% + 실습 70% 비율 유지
2. 프로젝트 기반 학습 (PBL): 실제 서비스 개발 경험 제공
3. 점진적 난이도 (Scaffolding): 기초 → 응용 → 심화 단계적 구성
4. 즉각적 피드백 (Immediate Feedback): 과제 제출 후 48시간 내 피드백
5. 협업 학습 (Collaborative Learning): 페어 프로그래밍, 코드 리뷰 문화

### 2.2 강의 구조 템플릿

#### 오전 강의 (09:30~12:30, 3시간)

| 시간 | 활동 | 비율 |

| 09:30~09:45 | 전일 복습 퀴즈 (5문제) | 8% |
| 09:45~10:30 | 이론 강의 (개념 설명) | 25% |
| 10:30~10:45 | 휴식 | - |

| 11:30~12:30 | 따라하기 실습 (수강생) | 33% |

|------|------|------|

### 2.3 라이브 코딩 가이드

강사의 라이브 코딩은 수강생 학습 효과에 직접적 영향을 미칩니다. 다음 규칙을 준수하십시오:

1. 타이핑 속도 조절: 일반 개발 속도의 50% 이하로 천천히
2. 생각 과정 설명: "여기서 왜 이 패턴을 쓰는지..." 식의 사고 과정 공유
3. 의도적 실수: 간헐적으로 에러를 만들고 디버깅 과정 시연
4. 수강생 참여 유도: "다음 줄에 뭐가 와야 할까요?" 질문
5. 코드 저장소 공유: 라이브 코딩 결과물은 당일 GitHub에 push

### 2.4 질문 대응 가이드

| 질문 유형 | 대응 방법 |
|----------|----------|
| 개념 이해 질문 | 비유 활용, 시각 자료 추가 설명 |
| 에러 해결 질문 | 힌트 제공 후 스스로 해결 유도 (5분 타이머) |
| 범위 외 질문 | 간단히 답변 후 "심화 자료" 링크 제공 |
| 반복 질문 | FAQ 문서화 후 LMS 게시 |
| 부정적 피드백 | 경청 후 개선점 기록, 다음 강의에 반영 |

### 2.5 수강생 수준 차이 대응

동일 과정 내에서도 수강생 간 수준 차이가 존재합니다:

- 상위 20% (빠른 학습자): 심화 챌린지 과제 별도 제공, 팀 프로젝트 시 기술 리드 역할 부여
- 중위 60% (평균 학습자): 표준 커리큘럼 충실히 진행
- 하위 20% (추가 지원 필요): 보충 자료 제공, 오피스아워 적극 활용 안내, 필요 시 1:1 추가 지도

현재 수강생 중 예시:
- 최도현(1996)은 3년차 개발 경력이 있어 AI/ML 과정에서 상위권, 동료 멘토 역할 수행
- 한수빈(2001)은 클라우드 DevOps 과정에서 네트워크 기초가 부족하여 보충 학습 진행 중
- 김지원(1998)은 비전공자이나 학습 열의가 높아 풀스택 과정 중위권에서 빠르게 성장 중

## 3. 커리큘럼 개발 프로세스

### 3.1 개발 주체 및 역할

커리큘럼 개발은 커리큘럼개발팀 정민재가 총괄하며, 다음과 같은 협업 구조로 운영됩니다:

| 역할 | 담당자 | 책임 |
|------|--------|------|
| 커리큘럼 총괄 | 정민재 (커리큘럼개발팀) | 전체 설계, 품질 검증, 버전 관리 |
| 과정별 SME | 각 과정 담당 강사 | 기술 내용 검증, 실습 자료 제작 |
| 산업 연계 | 한소영 (취업지원팀) | 채용 시장 트렌드, 기업 요구 역량 반영 |
| 예산 승인 | 오진우 (경영지원팀) | 자료 구매, 라이선스, 외부 강사비 |

### 3.2 커리큘럼 개발 사이클

#### 분기별 업데이트 (Quarterly Update)

1. 산업 트렌드 분석 (정민재)
   - Stack Overflow Survey, GitHub Octoverse 분석
   - 채용 공고 키워드 빈도 분석 (취업지원팀 데이터)
   - 수료생 피드백 수집 (한소영 코치 통해)

2. 강사 워크숍 (전 강사 참석)
   - 기존 커리큘럼 회고
   - 신기술 도입 여부 토론
   - 수강생 학습 데이터 분석 (완료율, 난이도 피드백)

3. 커리큘럼 초안 작성 (정민재 + 담당 강사)
   - 주차별 학습 목표 재정의
   - 실습 과제 신규 개발 또는 수정
   - 평가 기준 조정

4. 파일럿 테스트 (1주)
   - 졸업생 TA 또는 내부 직원 대상 시범 운영
   - 시간 배분, 난이도 적절성 검증

5. 최종 승인 및 배포
   - 정민재 최종 검토
   - 오진우 매니저 예산 승인 (신규 자료/라이선스 필요 시)
   - LMS 업로드 및 강사 브리핑

#### 긴급 업데이트 (Hotfix)

기술 스택의 메이저 버전 업데이트, 보안 이슈, 또는 수강생 다수 불만 시:
1. 담당 강사가 이슈 리포트 작성
2. 정민재 24시간 내 검토
3. 48시간 내 수정 반영 (LMS 업데이트)
4. 수강생 공지

### 3.3 커리큘럼 버전 관리

- 모든 커리큘럼 문서는 Git으로 버전 관리 (내부 GitLab)
- 브랜치 전략: main (현재 운영) / develop (다음 분기) / hotfix (긴급)
- 커밋 메시지 규칙: `[과정명] 변경유형: 설명`
  - 예: `[풀스택] feat: React 19 Server Components 모듈 추가`
  - 예: `[DevOps] fix: K8s 실습 환경 버전 불일치 수정`

## 4. 수강생 평가 체계

### 4.1 평가 원칙

1. 공정성: 동일 기준 적용, 강사 간 채점 편차 최소화
2. 투명성: 평가 기준 사전 공개, 결과에 대한 소명 기회 제공
3. 성장 지향: 절대평가 기반, 과정 내 성장폭도 고려
4. 다면 평가: 개인 역량 + 협업 역량 + 발표 역량 종합

### 4.2 평가 항목 및 배점 (공통)

| 평가 항목 | 비율 | 세부 기준 |
|----------|------|----------|
| 과제/프로젝트 | 60% | 기능 완성도, 코드 품질, 창의성 |
| 출석 및 참여도 | 15% | 출석률, 수업 참여, 질문 빈도 |
| 동료 평가 | 10% | 팀 프로젝트 기여도 (피어 리뷰) |
| 기술 면접 | 10% | 수료 전 모의 기술 면접 점수 |
| 일일 학습 기록 (TIL) | 5% | 성실도, 내용 깊이 |

### 4.3 과제 채점 루브릭

#### 코드 과제 채점 기준 (100점 만점)

| 항목 | 배점 | S (만점) | A (80%) | B (60%) | F (40% 이하) |
|------|------|---------|---------|---------|-------------|
| 기능 구현 | 40점 | 전체 요구사항 완벽 충족 | 핵심 기능 구현, 일부 미비 | 기본 기능만 구현 | 미제출 또는 실행 불가 |
| 코드 품질 | 25점 | 클린코드, 적절한 추상화 | 가독성 양호, 일부 중복 | 동작하나 구조 미흡 | 스파게티 코드 |
| 테스트 | 15점 | 높은 커버리지, 엣지 케이스 | 주요 로직 테스트 존재 | 1~2개 기본 테스트 | 테스트 없음 |
| 문서화 | 10점 | README 상세, 주석 적절 | README 존재, 기본 설명 | README 불충분 | 문서 없음 |
| 추가 구현 | 10점 | 창의적 기능 추가 | 일부 추가 시도 | 요구사항만 충족 | - |

### 4.4 팀 프로젝트 피어 리뷰

팀 프로젝트 종료 시 각 팀원은 다른 팀원에 대해 다음 항목을 평가합니다:

1. 기술적 기여도 (1~5점): 코드 작성량 및 품질
2. 협업 자세 (1~5점): 커뮤니케이션, 일정 준수
3. 문제 해결 (1~5점): 장애 상황 대처 능력
4. 리더십/팔로워십 (1~5점): 팀 분위기 기여

피어 리뷰 결과는 익명으로 처리하며, 팀 평균 대비 본인 평가가 현저히 낮은 경우 (하위 1 표준편차) 개인 면담을 진행합니다.

### 4.5 성적 이의 신청

- 제출 기한: 성적 공개 후 3영업일 이내
- 제출 방법: LMS 내 이의신청 게시판
- 처리 기한: 접수 후 5영업일 이내 결과 통보
- 재채점 시 정민재 (커리큘럼개발팀)가 최종 중재

## 5. 강사 성과 관리

### 5.1 평가 주기

- 분기별 정기 평가 (1월, 4월, 7월, 10월)
- 매 기수 종료 시 수강생 설문 기반 평가

### 5.2 평가 지표

#### 정량 지표 (60%)

| 지표 | 측정 방법 | 목표 |
|------|----------|------|
| 수강생 만족도 | 기수 종료 설문 (5점 척도) | 4.0 이상 |
| 수료율 | 수료 인원 / 등록 인원 | 85% 이상 |
| 취업률 | 수료 후 3개월 내 취업 | 85% 이상 |
| 과제 피드백 시간 | PR 리뷰 평균 소요 시간 | 48시간 이내 |
| 커리큘럼 기여 | 분기 업데이트 제안 건수 | 2건 이상 |

#### 정성 지표 (40%)

| 지표 | 평가자 | 비고 |
|------|--------|------|
| 강의 품질 | 정민재 (참관 평가) | 분기 1회 수업 참관 |
| 동료 협업 | 타 강사 상호 평가 | 익명 |
| 자기 개발 | 본인 보고 | 학습/컨퍼런스/기술 블로그 |
| 조직 기여 | 오진우 매니저 | 부가 활동 참여도 |

### 5.3 피드백 면담

분기별 평가 후 1:1 면담을 진행합니다:
- 면담자: 정민재 (교육 품질) + 오진우 (행정/처우)
- 소요 시간: 30~60분
- 논의 내용: 평가 결과 공유, 개선점 논의, 다음 분기 목표 설정
- 기록: 면담 내용은 경영지원팀에서 보관 (열람 제한)

### 5.4 개선 계획 (PIP: Performance Improvement Plan)

C 등급 2회 연속 시 PIP가 발동됩니다:
1. 구체적 개선 목표 설정 (측정 가능한 KPI)
2. 3개월 개선 기간 부여
3. 격주 1:1 점검 미팅 (정민재)
4. 기간 내 목표 미달성 시 계약 종료 검토

## 6. 수업 피드백 수집 및 반영

### 6.1 피드백 수집 채널

| 채널 | 주기 | 형태 | 담당 |
|------|------|------|------|
| 일일 만족도 | 매일 | 이모지 반응 (LMS) | 교육운영팀 |
| 주간 피드백 | 매주 금요일 | 객관식 + 주관식 설문 | 교육운영팀 |
| 중간 평가 | 과정 50% 시점 | 심층 설문 (30문항) | 정민재 |
| 종료 평가 | 수료 시 | 종합 설문 (50문항) | 정민재 |
| 자유 의견 | 상시 | Slack #피드백 채널 | 전 강사 |

### 6.2 피드백 분석 프로세스

1. 교육운영팀에서 주간 피드백 데이터 취합
2. 정민재가 트렌드 분석 (만족도 추이, 반복 불만 사항)
3. 담당 강사에게 분석 결과 공유 (매주 월요일)
4. 즉시 개선 가능한 사항: 해당 주 반영
5. 구조적 변경 필요 사항: 분기 커리큘럼 업데이트에 반영

### 6.3 피드백 반영 사례

#### 사례 1: AI/ML 과정 수학 모듈 난이도 조정
- 문제: 정하윤, 최도현 외 다수 수강생이 1~3주차 수학 복습의 난이도가 높다고 피드백
- 분석: 선수 조건 대비 미적분/선형대수 기대 수준이 과도
- 조치: 이준혁 강사와 협의하여 수학 기초 보충 자료 제작, 선택적 사전 학습 모듈 추가
- 결과: 다음 기수 해당 구간 만족도 3.2 → 4.1 상승

#### 사례 2: 풀스택 과정 팀 프로젝트 기간 연장
- 문제: 김지원, 이서준, 박민지 등 수강생이 2주 팀 프로젝트 기간이 부족하다고 건의
- 분석: 기획+개발+배포+발표를 2주에 완료하기에 시간 압박
- 조치: 13주차 Docker/CI 내용을 12주차로 압축, 프로젝트 기간 3주로 확대
- 결과: 프로젝트 완성도 향상, 수료작 포트폴리오 품질 개선

#### 사례 3: DevOps 과정 실습 환경 개선
- 문제: 한수빈 외 수강생들이 로컬 환경에서 K8s 실습 시 리소스 부족 호소
- 분석: 개인 노트북 사양으로 minikube 구동 시 메모리 부족
- 조치: 윤하린 강사 제안으로 판교캠퍼스 물리 서버에 공용 K8s 클러스터 구축
- 결과: 실습 원활, AWS EKS와 유사한 실제 환경 제공

## 10. 부록: 강사 행동 규범

### 10.1 윤리 강령

1. 수강생과의 사적 만남(음주, 1:1 식사 등)은 교육 기간 중 자제
2. 특정 수강생에 대한 편애 또는 차별 금지
3. 수강생 개인정보(연락처, SNS 등) 교육 목적 외 사용 금지
4. 경쟁사 비방 또는 특정 기업 편향적 추천 지양
5. 본인의 기술적 한계 솔직히 인정 ("확인 후 답변드리겠습니다")

### 10.2 지식재산권

- 강의 자료(슬라이드, 코드, 과제)의 저작권은 회사에 귀속
- 개인 기술 블로그에 강의 내용 재가공 게시 가능 (사전 승인 필요)
- 외부 강연 시 회사 커리큘럼 무단 활용 금지
- 오픈소스 활용 시 라이선스 준수 의무
